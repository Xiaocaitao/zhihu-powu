# 破雾工程契约与模块能力接口

## 一、核心原则

每个业务模块有两种对外能力：

```text
1. 面向其他业务模块：提供 TypeScript 函数或 Service 接口
2. 面向 Agent：通过 Tool 暴露，但 Tool 内部仍调用同一个 Service
```

不要为 Agent 单独复制一套业务逻辑，也不要让 Agent 直接操作数据库。

```text
其他模块
  → Module Service 函数
  → Repository
  → Database

Agent
  → Agent Tool
  → Module Service 函数
  → Repository
  → Database
```

## 二、推荐目录结构

每个业务模块都按下面结构组织：

```text
src/modules/<domain>/
  contracts.ts              # 输入、输出、领域类型
  service.ts                # 对其他模块提供的函数能力
  repository.ts             # Repository 接口
  postgres-repository.ts    # PostgreSQL 实现
  capabilities.ts           # 面向 Agent 的 Tool 能力适配
  migration.sql             # 数据表和索引
  tests/                    # 单元测试和集成测试
  README.md                 # 模块使用说明
```

队长统一维护：

```text
src/contracts/capability.ts
src/contracts/domain-events.ts
src/agent/runtime/
src/agent/tools/registry.ts
src/modules/chat/
```

## 三、模块对其他业务提供函数

模块间优先使用 Service 函数，不通过 HTTP 调 localhost。

统一上下文：

```ts
export type ModuleContext = {
  ownerId: string;
  sessionId?: string;
  requestId?: string;
  signal?: AbortSignal;
};
```

示例：学习模块向其他模块提供函数。

```ts
export interface LearningApplication {
  getActivePlan(
    ctx: ModuleContext,
    input: { includeTasks: boolean },
  ): Promise<LearningPlanDTO | null>;

  getOpenTasks(
    ctx: ModuleContext,
    input: { limit?: number },
  ): Promise<LearningTaskDTO[]>;

  updateTaskStatus(
    command: UpdateTaskStatusCommand,
  ): Promise<LearningTaskResult>;
}
```

职业模块可以调用学习模块的查询函数，首页聚合服务也可以调用这些函数：

```ts
const plan = await learningApplication.getActivePlan(ctx, {
  includeTasks: true,
});
```

模块之间只能依赖对方的 Service/Query 接口，不直接读取对方的表。

## 四、模块向 Agent 提供 Tool

Agent Tool 放在模块自己的 `capabilities.ts` 中，但 Tool 的执行逻辑必须委托给 Service。

示例：

```ts
export function createLearningCapabilities(
  service: LearningApplication,
): DomainCapability[] {
  return [
    {
      name: "get_active_learning_plan",
      description: "读取当前有效的学习计划和未完成任务",
      inputSchema: getActivePlanSchema,
      execute: (ctx, input) =>
        service.getActivePlan(ctx, input),
    },
    {
      name: "update_learning_task",
      description: "更新指定学习任务的状态",
      inputSchema: updateTaskStatusSchema,
      execute: (ctx, input) =>
        service.updateTaskStatus({
          context: ctx,
          payload: input,
          idempotencyKey: ctx.requestId,
        }),
    },
  ];
}
```

队长在主后台统一注册：

```ts
const capabilities = [
  ...createProfileCapabilities(profileService),
  ...createCareerCapabilities(careerService),
  ...createLearningCapabilities(learningService),
  ...createEvidenceCapabilities(evidenceService),
  ...createKnowledgeCapabilities(knowledgeService),
];

const tools = adaptCapabilitiesToPiTools(capabilities);
```

队员不需要修改 Agent Loop，也不需要直接依赖 Pi Agent SDK。

## 五、统一 Tool 上下文

`ownerId`、`sessionId` 等身份信息由队长的编排层注入，不由模型自行传入。

```ts
export type CapabilityContext = {
  ownerId: string;
  sessionId: string;
  requestId: string;
  sourceMessageId?: string;
  signal: AbortSignal;
};
```

## 六、统一命令格式

所有会写数据的 Tool 都使用命令格式：

```ts
export type DomainCommand<T> = {
  context: CapabilityContext;
  payload: T;
  expectedVersion?: number;
  idempotencyKey: string;
};
```

例如：

```ts
type UpdateTaskStatusCommand = DomainCommand<{
  taskId: string;
  status: "todo" | "in_progress" | "completed" | "paused";
  note?: string;
}>;
```

## 七、统一返回格式

```ts
export type CapabilityResult = {
  ok: boolean;
  changed: boolean;
  domain: string;
  entityId?: string;
  version?: number;
  status:
    | "read"
    | "applied"
    | "draft_created"
    | "confirmation_required"
    | "rejected";
  summary: string;
  data?: unknown;
};
```

示例：

```json
{
  "ok": true,
  "changed": true,
  "domain": "learning",
  "entityId": "task-001",
  "version": 4,
  "status": "applied",
  "summary": "已将任务标记为完成",
  "data": {
    "task_id": "task-001",
    "status": "completed"
  }
}
```

## 八、统一错误语义

```text
NOT_FOUND
FORBIDDEN
INVALID_ARGUMENT
INVALID_STATE
VERSION_CONFLICT
DUPLICATE_REQUEST
CONFIRMATION_REQUIRED
DEPENDENCY_UNAVAILABLE
```

每个模块需要在 `contracts.ts` 中定义自己的输入 Schema，并将错误映射到这些统一语义。

## 九、Query 与 Command 的区别

### Query：只读

例如：

```text
get_user_profile
get_career_plan
get_active_learning_plan
search_knowledge
get_learning_records
```

特点：

- 不修改业务数据；
- 可以由 Agent 自动调用；
- 返回当前用户可访问的 DTO；
- 必须校验 ownerId。

### Command：写入

例如：

```text
save_profile_fact
create_learning_plan
update_learning_task
record_learning_feedback
confirm_career_plan
record_learning_evidence
```

特点：

- 必须有权限、状态和幂等校验；
- 必须记录 requestId 或 toolCallId；
- 重要实体使用 expectedVersion；
- 高影响操作可以返回 `confirmation_required`。

## 十、一次完整交互示例

用户输入：

```text
我这周只有 4 个小时，数据库任务太难了。
```

Agent Loop：

```text
1. get_active_learning_plan
2. record_learning_feedback
3. adjust_learning_plan
4. 根据结果生成回复
5. 发送 domain_update
```

实际调用关系：

```text
Agent Tool
  → LearningApplication.recordFeedback()
  → LearningRepository
  → PostgreSQL
  → 返回 CapabilityResult
  → Agent 继续调用 adjustLearningPlan()
```

## 十一、首页更新协议

业务模块写入成功后，由队长统一发送：

```json
{
  "type": "domain_update",
  "domain": "learning",
  "resource": "plan",
  "entity_id": "plan-123",
  "version": 4,
  "change": "adjusted"
}
```

前端收到后重新请求：

```text
GET /api/home-summary
GET /api/learning/plans/current
```

前端不负责计算职业结论、任务进度和计划调整规则。

## 十二、模块说明

先保持轻量。每个队员只需要在模块的 `README.md` 或 `contracts.ts` 中说明三件事：

```text
1. 模块负责什么
2. 对其他模块提供哪些函数、对 Agent 提供哪些 Tool
3. 输入和输出示例
```
