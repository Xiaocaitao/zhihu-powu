# 学习计划模块开发计划（以 main 为基线）

## 1. 文档目的

本文是队员 C 学习计划模块的执行计划。本文不替代《队员 C-学习计划模块对接设计》，后者是固定的接口、Command、DTO、枚举、数据库表和业务规则规范。

本计划根据以下内容制定：

- 队员 C 的学习计划模块对接设计；
- 当前仓库最新 `origin/main`；
- 当前项目的统一 `ModuleContext`、`DomainCommand`、`CapabilityResult`、Agent Registry 和迁移运行机制；
- 队长已经完成的成长空间主流程和页面集成。

本计划的核心原则：

1. 以 `main` 已有架构和实现为基线，不重新创建平行的 Agent、HTTP 或页面架构。
2. 以队员 C 对接设计中的固定接口和七张表为验收标准，不用当前简化实现替代最终契约。
3. 先保护主线已有功能，再通过增量迁移和兼容改造补齐 Learning 领域缺口。
4. Learning 只保存 Profile、Career、Evidence 提供的 ID、版本和结构化摘要，不直接读取其他模块的表。

## 2. 固定规范和主线基线

### 2.1 固定规范

以下内容必须严格遵守队员 C 文档，不得自行更名或另设计一套接口：

- `LearningApplication` 的八个核心方法：
  `getActivePlan`、`getTodayTasks`、`getLearningProgress`、
  `createLearningPlan`、`updateTaskStatus`、`recordLearningFeedback`、
  `adjustLearningPlan`、`confirmLearningPlan`；
- Agent Tool：
  `get_active_learning_plan`、`get_today_learning_tasks`、
  `create_learning_plan`、`update_learning_task`、
  `record_learning_feedback`、`adjust_learning_plan`、
  `confirm_learning_plan`、`get_learning_progress`；
- 计划模式：`trial`、`final`；
- 计划状态：`draft`、`active`、`paused`、`completed`、`archived`；
- 任务状态：`todo`、`in_progress`、`completed`、`paused`；
- 任务类型：`reading`、`practice`、`project`、`review`；
- 七张固定表：
  `learning_plans`、`learning_stages`、`learning_tasks`、
  `learning_task_schedules`、`learning_feedback`、
  `learning_plan_adjustments`、`learning_idempotency_records`；
- 所有写操作的 `ownerId`、状态、幂等键和 `expectedVersion` 校验；
- 相同用户和相同幂等键的同载荷重放原结果，不同载荷返回 `DUPLICATE_REQUEST`；
- 试验计划未经确认不能替换正式计划；计划调整必须保留历史。

## 4. 目标架构

```text
Profile / Career / Evidence Service
              ↓ 只提供快照、ID、版本和测验摘要
队长 Agent / LLM
              ↓ 生成结构化计划或调整操作
Learning capabilities
              ↓ 参数校验、上下文注入、结果适配
LearningApplication / LearningService
              ↓ 状态、权限、版本、幂等、事务和历史
LearningRepository
              ↓
PostgreSQL 七张固定表
```

职责边界：

- Agent 负责收集上下文并生成结构化计划和调整操作；
- capabilities 只负责 Schema 校验、上下文转发和结果适配；
- Service 负责所有 Learning 业务规则；
- Repository 负责 Learning 数据持久化，不读取其他模块的表；
- Profile、Career、Evidence 继续由各自成员维护；
- 队长维护全局 Registry、Agent Runtime、主页面和 SSE 发布器。

### 阶段二：固定契约和 Learning 领域规则补齐（下一开发阶段）

目标：在 main 现有 Service 和 capabilities 架构上，补齐队员 C 文档规定的契约和业务行为。

#### 2.1 contracts

补齐并固定：

- `ModuleContext`、`DomainCommand` 和 `CapabilityResult` 的统一类型使用；
- `LearningPlanDTO`、`LearningTaskDTO`、`LearningProgressDTO`、`LearningFeedbackDTO` 等 C 文档 DTO；

- 日期、时长、文本长度、数组数量和版本号 Schema；
- `endDate >= startDate`；
- 所有操作的合法字段组合，禁止只声明 `adjustmentMode` 却不提供对应操作内容。

main 已有的 `get_learning_plan_drafts` 可以继续保留，作为确认流程的兼容扩展，但不得替换 C 文档规定的八个核心 Tool。

#### 2.2 Service

按 C 文档实现：

- 创建 `trial` 和 `final` 计划，保持用户隔离；
- 同一用户最多一个 `active final` 计划；
- trial 未确认前不替换 final；
- 任务状态合法转换和计划状态检查；
- 所有写命令检查 `expectedVersion`；
- 所有写命令执行同用户幂等键校验；
- 同键同载荷返回历史结果，同键不同载荷返回 `DUPLICATE_REQUEST`；
- 反馈任务必须属于反馈计划；
- 调整任务必须属于当前计划，非法状态和不存在任务不得静默忽略；
- 完整执行拆分、重排、改期、替换资源等固定操作；
- 计划调整成功后增加版本并写入调整历史；
- 确认 trial 时按规范处理旧 final 计划，并正确处理未完成任务；
- 进度、阶段进度和今日任务来自实际结构化数据。

### 阶段三：七表数据库增量迁移和 PostgreSQL Repository

目标：从 main 当前的简化 JSONB 存储迁移到队员 C 规定的七张表。

#### 3.1 迁移原则

- 不直接修改已经进入 main 的 `004-learning.sql` 和 `005-learning-sources.sql`；
- 迁移运行器会校验历史 SQL checksum，直接改历史文件会导致已部署环境启动失败；
- 使用下一个可用的增量迁移文件，例如 `006-learning-normalized.sql`，最终文件名以开发时仓库为准；
- 迁移必须可重复执行，且在一个数据库事务中完成结构和数据转换；
- 新 Repository 写入规范表，不能继续把新任务写入阶段 JSONB；
- 现有 JSONB 数据必须先转换并校验，再决定何时清理兼容字段；
- 不新增 C 文档未规定的业务表或替代表。

#### 3.2 目标表

必须具备以下表及 C 文档规定的字段、外键、索引和约束：

```text
learning_plans
learning_stages
learning_tasks
learning_task_schedules
learning_feedback
learning_plan_adjustments
learning_idempotency_records
```

重点约束：

- `learning_plans` 的 active final 唯一约束；
- stages、tasks、schedules 的归属关系；
- task status、task type、schedule status 的枚举约束；
- adjustment `to_version > from_version`；
- idempotency 主键为 `(owner_id, idempotency_key)`；
- 外部 Profile、Career、Evidence 只保存 ID 和版本，不复制外部明细。

#### 3.3 ownerId 兼容门槛

队员 C 文档中的 `owner_id` 定义为 UUID，而 main 当前匿名会话和部分成长模块使用字符串形式的 owner 标识。阶段三开始前必须先确认项目统一身份边界：

- 不能为了绕过差异而私自把 C 文档的 UUID 改成另一套业务表；
- 不能让 Learning Repository 直接读取 Profile 或用户表来猜测 owner；
- 如果主线统一身份已经确定为 UUID，按统一身份迁移现有数据；
- 如果主线仍需匿名字符串 owner，必须由队长确认统一的身份映射方案后再执行数据库迁移；
- 在身份方案未确认前，只完成不依赖真实数据库的 contracts、Service 和测试，不提交破坏性迁移。

#### 3.4 Repository

Repository 必须提供：

- 计划、阶段、任务、时间安排的查询和保存；
- 反馈保存；
- 调整历史保存和查询；
- 幂等记录查询和保存；
- 事务内的版本检查和写入；
- owner 隔离查询。
