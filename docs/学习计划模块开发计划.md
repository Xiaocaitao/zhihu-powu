# 学习计划模块开发计划

## 1. 文档目的

本文用于规划队员 C 负责的学习计划（Learning Plan）模块开发工作，作为后续页面开发、后端实现、测试和模块联调的执行依据。

本文根据以下内容整理：

- `队员C-学习计划模块对接设计(1).md`：Learning Plan 完整后端设计和模块对接约束；
- `docs/工程契约与模块能力接口.md`：项目统一的 Service、Tool、Command 和返回结果约定；
- `docs/成长空间模块分工.md`：队员 C 的负责范围；
- 当前项目的页面和服务端实现情况；
- 本次需求对第一版本的范围限制。

附件设计文档描述的是模块的最终目标，本计划将其拆分为多个阶段实施。第一版本不提前实现完整后端，也不负责主页面集成。

## 2. 开发结论

本模块采用**先页面、后后端、再联调**的分阶段开发方式。

原因：

- 第一版本明确只要求独立 HTML 页面、样式和 Mock 展示；
- Learning 后端包含计划、阶段、任务、反馈、调整、版本和幂等等多个业务边界；
- Profile、Career、Evidence 和队长 Agent 仍由其他成员负责；
- 先完成独立页面可以让页面结构和信息层级先被验收，减少与真实接口联调时的返工。

阶段顺序如下：

```text
阶段一：独立静态 HTML 页面 V1
  → 阶段二：Learning 后端契约与 Mock Service
  → 阶段三：业务规则测试与 Mock 流程验证
  → 阶段四：Profile / Career / Evidence / Agent 联调
```

## 3. 需求边界

### 3.1 当前版本必须完成

第一版本只完成学习计划模块的独立前端页面：

- 页面结构；
- 页面样式；
- 少量 Mock 数据展示；
- 计划、阶段、任务和进度的基本信息层级；
- 页面在桌面端和移动端的基本适配；
- 可脱离主页面独立访问。

### 3.2 当前版本明确不做

第一版本暂不完成以下内容：

- 不接入学习计划 API；
- 不连接数据库；
- 不读取真实 OAuth 用户数据；
- 不读取 Profile、Career、Evidence 的真实数据；
- 不实现真实的任务状态修改；
- 不实现真实的反馈提交和计划调整；
- 不实现 Agent Tool 注册；
- 不修改队长负责的 Agent Runtime、全局 Tool 注册表和 SSE；
- 不修改 `public/index.html`；
- 不负责将页面集成到主页面；
- 不修改其他模块页面。

### 3.3 附件设计文档中的后续目标

附件文档要求最终实现 Learning Plan 的完整后端能力，包括：

- `LearningApplication` 查询和写入接口；
- 计划、阶段、任务、任务时间安排；
- 学习反馈和计划调整历史；
- 试验计划与正式计划分离；
- `ownerId`、状态、`expectedVersion` 和幂等校验；
- Repository、PostgreSQL 实现和数据库迁移；
- 面向 Agent 的 Learning capabilities；
- 与 Profile、Career、Evidence 的 Service 对接。

这些内容作为阶段二至阶段四的实施依据，不作为阶段一已完成内容。

## 4. 阶段一：独立静态 HTML 页面 V1

### 4.1 交付文件

计划新增：

```text
public/learning-plan.html
```

当前服务端已经提供根页面和静态资源访问能力。为支持独立页面访问，需要在不影响现有主页面的前提下增加：

```text
/learning-plan.html
```

预期访问地址：

```text
https://powu-101-201-101-252.nip.io/learning-plan.html
```

页面的实际部署地址以部署环境配置为准；`?oauth=success` 仅属于基础站点的登录回调场景，第一版本页面不读取 OAuth 数据。

### 4.2 页面信息架构

页面按以下区域组织：

#### A. 计划头部

展示：

- 页面标题；
- 计划状态；
- 计划模式；
- 计划版本；
- 计划 ID；
- 目标岗位；
- 计划开始日期和结束日期；
- 每周预计学习时长。

用户、岗位、ID、版本和日期均使用占位符，不写真实用户信息。

#### B. 计划进度概览

展示：

- 计划总体完成百分比；
- 任务总数；
- 已完成任务数；
- 当前阶段；
- 当前阶段完成百分比；
- 本周预计学习时长。

阶段一只展示 Mock 结果，不计算真实业务进度。

#### C. 阶段路线

每个阶段展示：

- 阶段顺序；
- 阶段名称；
- 阶段目标；
- 阶段日期；
- 阶段状态；
- 阶段进度；
- 是否需要阶段测验。

阶段应能体现从当前阶段到目标阶段的连续路线，但不在前端推断用户能力或职业结论。

#### D. 两周学习计划

任务展示字段：

- 学习日期；
- 任务标题；
- 任务描述；
- 任务类型；
- 预计时长；
- 当前状态；
- 完成标准；
- 是否需要成果证据。

任务类型使用设计文档中的枚举语义：

```text
reading   阅读
practice  练习
project   项目
review    复盘
```

#### E. 今日任务

展示当天需要关注的任务：

- 任务标题；
- 所属阶段；
- 预计时长；
- 任务状态；
- 今日安排时间；
- 完成标准。

阶段一的日期可以使用展示占位符，不绑定真实当前日期。

#### F. 反馈和调整入口

提供视觉上的操作入口：

- 汇报进度；
- 遇到问题；
- 调整计划。

阶段一只展示入口和页面状态，不提交 API，不改变 Mock 数据。

#### G. 调整历史

展示计划调整记录的基本结构：

- 调整时间；
- 调整触发原因；
- 调整说明；
- 调整前版本；
- 调整后版本；
- 变更摘要。

阶段一只展示少量示例记录，不实现真实版本变更。

### 4.3 Mock 数据规则

Mock 数据必须满足以下规则：

- 只覆盖页面展示所需的基本场景；
- 数据量保持精简；
- 任务标题和任务描述不得重复；
- 至少覆盖 `todo`、`in_progress`、`completed`、`paused` 四种任务状态；
- 至少覆盖不同任务类型；
- 阶段状态和任务状态之间保持基本合理；
- 不出现真实姓名、真实岗位、真实用户 ID 或真实计划 ID；
- 字段缺省时使用占位符，不自行编造其他模块数据；
- Mock 数据只用于展示，不作为后端默认业务数据。

建议使用以下占位表达：

```text
[用户名称]
[目标岗位]
[计划 ID]
[计划版本]
[开始日期]
[结束日期]
[每周学习时长]
```

### 4.4 页面交互边界

阶段一允许实现不依赖 API 的展示交互，例如：

- 任务状态筛选；
- 阶段展开和收起；
- 今日任务与全部任务切换；
- 页面内反馈入口的静态弹窗或提示；
- 响应式布局。

阶段一禁止实现：

- 发送网络请求；
- 修改数据库；
- 将状态持久化到浏览器或服务端；
- 根据用户输入生成计划；
- 在页面脚本中实现后端业务决策。

### 4.5 阶段一验收标准

满足以下条件后，阶段一视为完成：

- `public/learning-plan.html` 文件存在且可以独立打开；
- 页面可以通过 `/learning-plan.html` 访问；
- 页面不依赖 `public/index.html` 的 DOM 或脚本；
- 页面包含计划、阶段、任务、进度、反馈和调整历史等核心区域；
- Mock 数据覆盖基本任务状态且不存在重复任务；
- 用户字段使用占位符，没有真实用户数据；
- 页面不调用 API、不连接数据库、不读取 OAuth；
- 桌面端和移动端无明显重叠、溢出或内容遮挡；
- 页面视觉风格与当前项目保持一致；
- 不修改其他模块界面和主页面集成逻辑。

## 5. 阶段二：Learning 后端契约与 Mock Service

阶段一验收通过后，再按照附件设计文档实现后端模块。

### 5.1 计划目录

```text
src/modules/learning/
  contracts.ts
  service.ts
  repository.ts
  postgres-repository.ts
  capabilities.ts
  tests/
  README.md

src/db/migrations/004-learning.sql
```

### 5.2 后端职责

Learning 模块负责：

- 保存 Agent 生成的结构化试验计划或正式计划；
- 保存计划阶段和学习任务；
- 查询当前有效计划；
- 查询指定日期的学习任务；
- 更新任务状态和实际用时；
- 保存用户学习反馈；
- 执行结构化的计划调整操作；
- 保存计划调整历史；
- 计算计划和阶段完成度；
- 执行用户隔离、状态、版本和幂等校验。

Learning 模块不负责：

- 生成职业结论；
- 判断用户应该学习什么；
- 直接调用知乎搜索；
- 直接读取 Profile、Career、Evidence 数据表；
- 实现阶段测验和成果证据；
- 修改队长的 Agent Runtime 和全局事件发布器。

### 5.3 Service 能力

后端至少实现以下 `LearningApplication` 能力：

```text
getActivePlan
getTodayTasks
getLearningProgress
createLearningPlan
updateTaskStatus
recordLearningFeedback
adjustLearningPlan
confirmLearningPlan
```

面向其他模块的调用必须经过 Learning Service，不能直接读取 Learning 数据表。

### 5.4 Mock Repository 验证范围

在接入 PostgreSQL 前，先使用 Mock Repository 验证：

- 创建 `trial` 计划；
- 创建 `final` 计划；
- 查询当前计划和任务；
- 查询今日任务；
- 更新任务状态；
- 记录实际用时；
- 记录学习反馈；
- 拆分任务；
- 调整任务日期；
- 调整任务顺序；
- 替换任务资源；
- 保存调整历史；
- 确认试验计划；
- 计算计划和阶段进度；
- 同一用户的数据隔离；
- 非法状态流转拒绝；
- `expectedVersion` 版本冲突；
- 相同幂等键重放原结果；
- 相同幂等键提交不同载荷时返回重复请求错误。

### 5.5 后端统一约束

写操作必须遵守项目统一契约：

- `ownerId` 从上下文注入，不能由 Agent 或前端传入；
- 写命令必须有幂等键；
- 重要实体必须校验 `expectedVersion`；
- 计划调整必须写入历史；
- `trial` 计划未经用户确认不能替换 `final` 计划；
- 其他模块只能调用 Service，不得直接访问 Learning Repository；
- Agent Tool 只能调用 Service，不得直接访问数据库。

## 6. 阶段三：测试与 Mock 流程

### 6.1 测试重点

测试应覆盖：

- contracts 的输入校验；
- 日期格式和时间范围；
- 任务类型和状态枚举；
- 计划模式和状态；
- 计划进度计算；
- 阶段进度计算；
- 任务状态更新；
- 反馈保存；
- 调整历史可追溯；
- 试验计划确认；
- 版本冲突；
- 用户隔离；
- 幂等重放；
- 非法参数和非法状态错误映射。

### 6.2 推荐开发顺序

```text
contracts
  → Mock Repository
  → service
  → Service 单元测试
  → capabilities 参数适配
  → PostgreSQL Repository
  → 数据库迁移测试
```

在 Mock 流程通过前，不接 Profile、Career 和 Evidence 的真实 Service。

## 7. 阶段四：模块联调

### 7.1 Profile

Learning 只消费 Profile 快照和版本号：

- 当前能力或已学内容；
- 每周可投入时间；
- 可选的可学习时间段；
- 学习偏好；
- Profile 版本。

没有可用时间或画像时，不应静默编造正式计划。

### 7.2 Career

Learning 只消费 Career 快照和版本号：

- 目标岗位 ID；
- 目标岗位名称；
- 能力差距；
- 优先能力；
- 推荐项目；
- 截止时间。

Learning 不自行计算岗位匹配度或职业结论。

### 7.3 Evidence

Learning 只消费阶段测验摘要：

- 测验 ID；
- 阶段 ID；
- 得分；
- 是否通过；
- 薄弱能力；
- 调整建议。

Learning 不实现测验评分和成果证据逻辑。

### 7.4 队长 Agent/Core

由队长负责：

- 注册 Learning capabilities；
- 将 Tool 接入 Agent；
- 统一发布 `domain_update`；
- 首页聚合学习计划；
- 主页面集成独立 HTML 的内容或样式；
- 处理全局 SSE 和 Agent Runtime。

Learning 模块只提供约定好的 Service、Tool 适配和领域事件内容，不直接修改全局注册和运行时。

## 9. Git 协作流程

### 9.1 分支

本模块在以下分支开发：

```text
dev-Struggle871
```

不得直接向远程 `main` 开发或推送。

### 9.2 每次开发前

```text
1. 拉取 origin/main
2. 切换或建立本地 dev-Struggle871
3. 将最新 main 合并到 dev-Struggle871
4. 检查工作区和待提交改动
```

如果网络原因无法拉取远程 `main`，必须在开发记录中说明，不能把旧的远程引用表述为最新状态。

### 9.3 每个版本完成后

```text
1. 运行与本版本范围匹配的检查和测试
2. 再次拉取 origin/main
3. 将最新 main 合并到 dev-Struggle871
4. 创建本地 commit
5. 不自动推送
```

### 9.4 Commit message

根据 `AGENTS.md`，每条提交信息必须说明本次需求解决了什么问题，格式使用：

```text
<type>: <需求描述>
```

推荐提交信息：

```text
feat: 创建学习计划模块独立静态页面结构与样式
feat: 建立学习计划模块领域契约与 Mock 服务
test: 补充学习计划状态流转与进度计算测试
feat: 增加学习计划 PostgreSQL 存储与数据库迁移
```

### 9.5 推送规则

- 开发完成后只创建本地提交；
- 推送前必须再次拉取并合并 `main`；
- 准备推送时先提醒项目负责人；
- 获得确认后只推送 `origin/dev-Struggle871`；
- 不推送远程 `main`；
- 由项目负责人创建和提交 Pull Request。
